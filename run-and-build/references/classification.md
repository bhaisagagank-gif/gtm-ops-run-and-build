# Classification

Classify every incoming item into exactly one class, and mark it RUN (keeping existing operations running) or BUILD (creating new capability).

## Classes

### P0 — Critical
Revenue, core operations or compliance are disrupted **right now**.

Examples: inbound leads not reaching the CRM; lead routing down across the board; scheduler integration failed for all bookings; a critical campaign launch blocked by a system failure; an active data-privacy or compliance breach.

Not P0: someone writing "urgent"; a single failed sync with no lead loss; a request with a tight deadline but no disruption (that is P1).

Expected action: investigate immediately, find the business impact and affected people, contain the damage (a manual workaround is fine), fix the root cause, communicate status.

### P1 — Important
Meaningful business impact, stakeholder commitments or near-term deadlines.

Examples: a paid landing page live without its form connected; a campaign with a launch date; leads routing to the wrong owner for a segment; leadership reporting; a recurring data-quality problem with visible impact.

Expected action: assess impact, deadline, effort and dependencies; schedule it; say what moves to make room.

### P2 — Routine
Useful but not urgent.

Examples: one-off list pulls; minor field changes; cosmetic fixes; non-urgent research; vendor deadlines weeks away.

Expected action: batch, defer, redirect or automate. Challenge requests that don't justify the effort.

### S — Strategic
Capability-building **projects and playbooks** that create long-term value for the company: signal engines, scoring, lifecycle redesign, integration architecture, platform replacements.

Not strategic: campaigns (classify by deadline and impact as P1 or P2), one-off reports, personal productivity projects, career development.

S is a type, not an urgency level. Manage strategic items in a separate portfolio (see `strategic.md`).

### Not mine
Work that belongs to another team or person. Name the likely owner and recommend redirecting. Keep it on record so the request isn't lost.

## Edge cases

| Situation | Classification |
|---|---|
| Automated error alert, first time | Notification — monitor, don't log |
| Same alert repeating for days | Mention once as a pattern; log a task only if someone must fix it |
| Meeting brainstorm with no agreed owner | Not logged; note it as an open question if useful |
| Meeting notes "suggested next steps" generated by AI | Treat as suggestions; confirm before treating as commitments |
| Request from a senior person with no business impact | Classify by impact, not seniority |
| Item already fixed by someone else | Resolved; record who fixed it |
| User says "this isn't mine" | Not mine, and remember the rule for similar items |
| Waiting on a vendor or another team | Keep the class; set status "Waiting on [name]" (pauses the SLA clock) |

## Standing rules

Users add their own rules to `ops-config.md` as they learn them. Apply them before the defaults. Examples:

- "Issues in the booking workflow are never P0; classify as P1."
- "Billing problems for tool X belong to team Y — Not mine."
- "Workflow error alerts are notifications, not tasks."
- "Campaigns are never Strategic."
